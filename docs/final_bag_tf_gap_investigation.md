# 決勝bagの `map → base_link` TF欠落調査

## 対象と方法

- bag: `rosbag2_2026_09_20-16_25_27_0-004.db3`
- 区間: bag記録開始から `936.3–1116.3 s`（180秒）
- SQLiteの記録時刻と、ROSメッセージの `header.stamp` を分けて集計した。
- `/livox/lidar`、`/livox/imu`、`/platform_constraint`、`/tf`、`/dynamic_cloud`、`/rosout` を照合した。

## 結論

bagに元からある `map → base_link` TFの空白は、LiDARやIMUの停止ではなく、自己位置推定ノードがマッチング結果を採用できず、姿勢とTFを配信しないために発生している。最長の空白でもグローバル探索は各点群で動いており、探索コストが採用しきい値を超え続けている。bagの `--start-offset` 再生や静的TFの欠落だけで生じた空白ではない。

これは直接原因の特定であり、コスト上昇の物理的な原因（遮蔽、動的物体、地図とのずれなど）や空白中の絶対位置は未確定である。

## 根拠

| 記録時刻の180秒間 | 件数・最大間隔 |
| --- | ---: |
| `/livox/lidar` | 1,800件、点群の `header.stamp` 間隔は最大約0.102秒 |
| `/livox/imu` | 36,001件、`header.stamp` 間隔は最大約0.009秒 |
| `/platform_constraint` | 1,253件 |
| `map → base_link` の `/tf` | 1,253件、最大stamp間隔4.0秒 |
| `/dynamic_cloud` | 1,801件。窓の両端で入力点群との件数が1件ずれる |

`/platform_constraint` と `map → base_link` は同じ姿勢更新から配信される。最長のTF空白はstamp `966.18 → 970.18 s`。対応する記録時刻 `966.54 → 970.26 s` にはグローバル探索がほぼ0.1秒ごとに完了しているが、コストは概ね `0.016–0.050` で、最後の `0.0110` で復帰している。次の長い空白 `976.48 → 980.08 s` でも同様に探索が続き、`0.0104` で復帰した。

同区間の自己位置推定ログには、ローカルマッチング失敗が215件、ロスト移行が80件、グローバル探索の開始・完了が各413件、復帰が80件記録されている。`TF lookup failed`、障害物点数不足、GPU探索失敗のログはなかった。全体の点群件数とTF件数の差は547件。ただし記録時刻の区間端による1件程度のずれがあるため、各失敗ログの合計と厳密に同一視しない。

実装上、`cloudCallback()` はマッチングが成立し、かつ `best_cost < cost_threshold` のときにのみ `publishPoseAndTransform()` を呼ぶ。一方、`/dynamic_cloud` はマッチング失敗時にも配信する。したがって動的点群が流れていても `map → base_link` が止まる。関連箇所は `src/localization_node.cpp` の `cloudCallback()` と `publishPoseAndTransform()`。

## 再生時の補足

このbagの `base_link → livox_frame` 静的TFは区間開始より前（約900.33秒）に記録されている。`moving_bucket_rviz.launch.py` の `bag_static_tf_replayer` はこれを読み直して配信する。一方、欠けている動的な `map → base_link` はこの仕組みでは補えない。

同じ点群stampを持つLiDARとTFの記録時刻差は、区間内で照合できた1,251件で中央値約0.076秒、95パーセンタイル約0.115秒、最大約0.543秒。検出器のTF待機時間設定は `0.9秒`。stamp時刻で「次に使えるTFまで0.9秒を超える」点群は180秒内に168件あり、報告されたTF不足による194件の破棄と規模が合う。168件はbagのstampだけからの概算であり、再生時のキュー、到着順序、TFバッファ状態を再現した件数ではない。

bag中のログはロスト判定を `1/2`、`2/2` と表示するが、現在のリポジトリの `config/localization_params.yaml` は `lost_count_thresh: 10` である。記録時の有効なパラメータファイルまたは上書き値はbagから確定できない。採用しきい値はログの失敗・復帰コストから約`0.015`と整合するが、これも記録時のパラメータ値としては確証がない。

## 次の実験

1. 決勝時の起動コマンドとパラメータファイルを特定し、実効値（特に `cost_threshold`、`lost_count_thresh`、探索範囲）を保存する。
2. LiDARフレームごとに障害物点数、最良コスト、採否、推定姿勢、処理時間を記録する。現在のログだけではコスト上昇の理由を区別できない。
3. ロスト区間の点群を可視化し、静的地図に合う点と動的物体・遮蔽を分けて評価する。しきい値を変更する場合は、連続性だけでなく誤った位置への復帰も同時に検証する。

空白中に姿勢TFを補間・外挿する場合は、観測に基づく自己位置と区別して扱う必要がある。
