# 決勝bagの点群とフィールド地図の位置合わせ

## 地図の基準

競技フィールド図面 `robocot26_field421.pdf`（2026年4月15日版）の競技領域は
11.4 m × 10.5 m、フェンス外形は11.7 m × 10.8 m、中央の仕切りは
幅0.6 m・高さ0.2 m。リポジトリの地図では図面の10.5 m方向をmapのx、
11.4 m方向をmapのyとしている。`/field_map_markers` は
`config/nhk2026_map.json` の箱・円柱を表示する。

図面の外周フェンスは幅150 mmのL字断面で、LiDARが主に見る立ち上がりは
約24 mm厚の面である。現在の地図は幅100 mmの箱で近似している。
図面には造作物の施工誤差がある旨も明記されている。このため、図面の外形寸法を
そのままマッチング箱の厚みや中心位置へ代入しない。実測したフェンス面、
机・椅子の実際の形、LiDARの外部パラメータを確認してから地図を校正する。

## ずれの調査

決勝bagの `936.3–1116.3秒` の旧 `/platform_constraint` と
`/livox/lidar` を同じヘッダー時刻で照合した。静的TF
`base_link → livox_frame = (0.2, -0.25, 1.09) m` を適用し、
GN10と同じ距離・機体・地面フィルタをCPUで再現した。20件に1件の旧姿勢、
計63フレームを評価した。旧姿勢は正解ラベルではない。

| 評価 | 63フレームの中央値 |
| --- | ---: |
| 従来の符号付き箱距離の平均残差 | 0.032 m |
| 箱の表面までの非負距離の平均残差 | 0.123 m |
| 負の残差を生む点の割合 | 43.1% |

旧CUDA実装は箱の**内部**にある点の距離を負のまま積算していた。
外側の点の正の距離を相殺できるため、コストが小さいことは地図への一致を
意味しない。同じbagの旧姿勢で外周点を集計すると、yの正側の壁のピークは
約+5.775 m、負側は約-5.62 mで、中心が約+0.08 m寄っていた。
新しい非負距離で同じ点群を局所最適化すると、y補正は多くのフレームで
負方向へ約数cmから十数cmだった。これは旧マッチングの系統ずれを示唆するが、
実測真値との差とは扱わない。

初回の実GPU再生では、領域外へ動かした点をコスト平均から除外する実装も
全域探索の誤対応を招いた。修正後は領域外の点も最大距離の残差で積算し、
常に入力点数で割る。しきい値はこの非負・全点平均コスト用に変更した。
左右に似た配置があるため、点群1枚から開始位置を確定できない場合は
`initial_pose_local_search:=true` と既知の開始姿勢を指定する。

## 決勝bagの再生

ビルド後、別々の端末で次を実行する。旧bag内の `/tf` と
`/platform_constraint` は再生しない。

```bash
source ~/ros2_ws/install/setup.bash
ros2 launch gn10_pointcloud_localization fast_lio_fusion.launch.py \
  use_sim_time:=true initial_pose_local_search:=true \
  initial_pose_x:=-4.74 initial_pose_y:=-1.68 initial_pose_yaw:=1.54
```

```bash
source ~/ros2_ws/install/setup.bash
ros2 bag play '/home/lambda/bag_files/地区大会/rosbagjetson6/rosbag2_2026_09_20-16_25_27_0-004.db3' \
  --clock --start-offset 936.3 --topics /livox/lidar /livox/imu
```

開始姿勢はbagに記録された旧出力の概略値であり、真値ではない。
初回の局所マッチングで補正するための探索中心としてのみ使う。
`/platform_constraint_raw` が出ても融合で採用されたとは限らないので、
`/gn10_pose_fusion/diagnostics` の `matches_accepted` と
`last_accepted_age_s` を確認する。RVizでは `Fixed Frame=map`、
`/field_map_markers` と `/obstacle_cloud` を重ねる。
`/obstacle_cloud` は実際にマッチャーが使う機体座標の障害物点群で、
RVizに購読者がいる時だけGPUからコピーして配信する。

## 実GPU再生の結果（2026年9月26日）

RTX 4060上で上記開始姿勢を使い、LiDAR・IMUのみを2倍速で再生した。
`936.3–1116.3秒` の180秒間に、生マッチング姿勢1,797件、
融合姿勢1,792件、FAST-LIOオドメトリ1,792件を記録した。
融合姿勢の最大配信間隔は約0.201秒、隣接姿勢の最大位置差は
約0.271 mで、0.5 mを超える跳びはなかった。区間終盤の診断では
地図観測1,779件中1,773件を採用し、イノベーションゲート棄却は0件、
最後の採用から約0.16秒だった。診断は1秒ごとの値なので、全区間末尾までの
最終累積数ではない。

旧姿勢と修正後の生マッチング姿勢が揃う63フレームを、同じ入力点群と
同じ非負・全点評価式で再計算した。平均残差の中央値は旧0.156 mから
修正後0.148 mへ下がった。外周の対向するy壁の観測ピークから求めた
中心ずれは旧約+0.075 mから修正後約+0.015 mとなり、融合姿勢でも
約+0.015 mだった。x壁の中心ずれは融合姿勢で約-0.015 m。
これらは図面のフェンス中心線とbag内の点群との整合性であり、
測量した実フィールドに対する絶対誤差ではない。

地図が図面の設計寸法に基づくこと、フェンスを箱で近似していること、
LiDAR外部パラメータが実機校正値ではないことから、全ての点を
「完璧に一致」させる数値保証はできない。実フィールド上の複数の基準点を
測量し、独立した真値軌跡と照合することが最終的な精度検証になる。
